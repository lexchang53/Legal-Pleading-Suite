# ⚖️ AI 法律訴訟書狀與研究自動化套件 (Legal Pleading Suite)
[![License: CC BY-NC-SA 4.0](https://img.shields.io/badge/license-CC--BY--NC--SA--4.0-lightgrey.svg)](LICENSE.md)
![Monorepo](https://img.shields.io/badge/structure-monorepo-blue)
![Taiwan Legal Workflow](https://img.shields.io/badge/focus-Taiwan%20Legal%20Workflow-2f855a)

本專案面向台灣法律實務工作者（律師、法務主管、司法研究者），整合 AI 爭點研究、官方裁判檢索、書狀撰寫、表格排版與 ODT 轉檔，形成一套模組化、可重複驗證的訴訟文件自動化工作流。

本專案的核心重點不是單一 Prompt，而是把複雜的法律工作徹底解耦為標準流水線：
**「案卷解析 ➔ 漸進式爭點研究與攻防沙盤推演 ➔ 官方裁判與實務檢索 ➔ 策略備忘錄固化 ➔ CRAC 訴狀/意見書生成 ➔ 專業 Word/ODT 排版」**。

> [!WARNING]
> **免責聲明**：本專案是法律工作輔助工具，不替代律師或使用者的專業判斷。任何草稿、書狀、附表或轉檔結果，在對外使用或提交法院前，仍應由使用者自行核對案件事實、法律依據、裁判引用、證據標號、頁碼與格式。

## 🌟 專案特色

- **研究與排版解耦**：將「法律攻防思維」與「嚴苛格式排版」分離，避免 AI 在長對話中因負荷過載而產生幻覺或格式跑版。
- **漸進式爭點研究**：以爭點為單位展開人機多輪協同互動，攻防推演拍板後即時固化至策略備忘錄（`strategy_memo.md`）。
- **專業級裁判檢索與驗證**：整合 `tw-legal-rag` 引擎，具備「要件+效果」精準公式、正反雙向查證、四類法源嚴格隔離與審級廢棄過濾。
- **嚴謹的訴訟書狀論證架構**：草稿嚴格遵循 CRAC 論證格式、四層級大綱編號、狀首動詞表、年份紀元規範與證據接續編號。
- **表格型法律文件支援**：可輸出符合臺灣高等法院格式之爭點整理表、聲請調查證據表與 7 欄高院證據清單表。
- **DOCX / ODT 雙路徑**：以 DOCX 為主輸出，並透過進階 XML 堆疊修復原生支援 LibreOffice 之 Tab/Shift-Tab 大綱升降級與外側（Outside）行編號。
- **Monorepo 整合管理**：將研究、撰狀、表格、轉檔與卷證工具集中管理，便於維護與擴充。

## 💡 為什麼重構為解耦流水線？（架構演進考量）

在先前的版本中，系統曾嘗試將外部查詢與書狀排版全部擠在同一個書狀技能中，本次重構為「研究（`legal-research`）➔ 排版（`draft-pleading`）」標準流水線，主要基於以下實務考量：

1. **職責分離與減輕 Context 負擔**：
   舊架構將「爭點探討」、「法源檢索」與「書狀排版」全部塞在同一個技能中，導致 AI 的系統提示詞（Prompt）過於沉重，在產出長篇書狀時容易遺忘嚴格的排版格式或產生推論幻覺。
2. **擺脫脆弱的瀏覽器自動化依賴**：
   舊版依賴無頭瀏覽器模擬登入爬取網頁，極易因介面改版、Cookie 過期、網路延遲而中斷失敗。
3. **原生 CLI 與裁判檢索專用工具的確定性**：
   改採專為台灣法律設計的 `tw-legal-rag` 原生 CLI 工具後，查詢速度達到毫秒級，且能直接取得精準的裁判字號、法官理由全文、審級歷史（廢棄檢驗）與引用封包驗證，使整條流水線具備極高的工程穩定度與法律真實性。

## 🎯 適用情境

本專案特別適合以下工作場景：

- 收到複雜案卷時，進行事實梳理、實體與程序爭點拆解、訴訟攻防策略擬定。
- 檢索臺灣法院歷年裁判、憲法裁判、主管機關函釋，並進行正反雙向案例查證。
- 撰寫民事起訴狀、答辯狀、準備書狀、上訴理由狀、憲法審查聲請書。
- 撰寫提供給客戶或企業內部的函文式法律意見書、契約審核風險分析備忘錄。
- 整理爭點、證據鏈與既有卷證，並延續同案既有書狀之證據編號脈絡。
- 需要輸出臺灣高等法院標準格式之證據清單、爭點整理表或調查證據表。
- 清理法院閱卷室掃描卷宗或電子卷證之浮水印與動態時間戳記。

## ⚖️ 本套件 `twlegalrag-search` 與原作者 Skill 之功能差異

本專案的檢索模組基於 [tw-legal-rag](https://github.com/aa0101181514/tw-legal-rag) 開發，針對實務研究流程增加了以下防禦規則與檢查機制：

1. **查詢詞結構化與口語簡寫處理**：
   - 強制採用「法律構成要件關鍵字 ＋ 法律效果關鍵字」（如 `競業禁止 違約金 過高`），限制查詢詞任意擴展（如 終止≠解除、無效≠撤銷）。
   - 使用者輸入「法院簡稱＋非標準案號」（如 `北院 112訴100`、`最高院 112台上100`）時，AI 會在查詢前自動補全為標準格式（如 `臺灣臺北地方法院 112年度訴字第100號`），避免系統無法辨識案號而退化為全文搜尋。
   - 支援最高法院大法庭（`台上大`、`台抗大`）與最高行政法院（`上大`、`抗大`）分案字號。
2. **強制正反雙向查證**：
   - 檢索正面支持案例時，同步加入反向關鍵字（如 `駁回`、`敗訴`）檢索對造抗辯與不利見解，避免研究結論落入盲點。
3. **裁判 CLI ＋ 行政函釋 MCP 雙軌分流**：
   - 司法裁判與勞動裁決由本地 CLI 處理；78 個中央部會之行政令函與規則由遠端 MCP 處理。
   - 引用函釋時主動查驗效力狀態，排除已廢止或停止適用之令函。
4. **法源類型隔離與審級過濾**：
   - 明確區分憲判字/釋字、法院裁判、行政函釋與勞動裁決，禁止將函釋或勞動裁決標註為法院判決。
   - 依法院審級排序，並排除經上級審廢棄之無效裁判。
5. **搜尋結果預覽與同字號消歧義**：
   - 在打包法源前，AI 會先展示搜尋摘要，並主動核對「跨分院同號案件」（如 `112上易100`）與「最高法院同字號民刑事案件」（如同為 `115台上176` 的民事與刑事判決），確認目標案件後再進行後續引用。

## 📚 私有知識庫擴充：Gemini Notebook、notebooklm-py 與 Obsidian

若您習慣將個人承辦案件的卷證資料、開庭筆錄、訪談音檔逐字稿或自行整理的法學筆記存放在私有知識庫中，本套件亦能完美搭配各類線上與本機方案：

### 1. 方案 A：Gemini Notebook (NotebookLM)
- **特色**：Google 原生 Gemini 2.5 驅動，適合直接上傳大型案卷檔案進行多文檔綜整。
- **專屬技能**：可安裝社群開源技能 [PleasePrompto/notebooklm-skill](https://github.com/PleasePrompto/notebooklm-skill) 或 [notebooklm-mcp](https://github.com/PleasePrompto/notebooklm-mcp)。
- **提示詞範例**：
  ```text
  請先讀取我 Gemini Notebook (NotebookLM) 中的「甲○○請求給付資遣費事件筆記本」，提取對造在上次準備程序中的主要抗辯點，並與工作區的案卷進行爭點比對。
  ```

### 2. 方案 B：極速查詢替代工具 `notebooklm-py`
- **特色**：針對 NotebookLM 瀏覽器查詢速度較緩慢之痛點，社群開發了非官方 Python API / CLI 工具 **[notebooklm-py (teng-lin)](https://github.com/teng-lin/notebooklm-py)**，支援直接透過指令或 API 高速檢索 NotebookLM 筆記本，適合追求極速響應之使用者自行整合。

### 3. 方案 C：本機知識庫（如 Obsidian 等）
- **特色**：Obsidian **100% 原生支援直接存放與內嵌 PDF 卷證**、Markdown 筆記與錄音檔，且具備本機資料絕對隱私安全之優勢。
- **使用方式**：使用者可將案件工作區直接建立在 Obsidian Vault 內，或透過本機文件搜尋讓 AI Agent 直接讀取資料夾內的 PDF 與 Markdown 筆記。

> [!NOTE]
> 以上私有知識庫與外部技能均為選配擴充，使用者可依辦案習慣與隱私偏好自行選擇與設置。

## 🛠️ 環境安裝與先備依賴

### 1. 先備條件

建議您至少具備以下環境：

- 具 **Agentic 能力** 的 AI Agent 或 AI Coding Assistant（推薦如 Google Antigravity、Claude Code、Codex app 等），且以具有 IDE 或類 IDE 工作介面者為佳。
- Python 3.10+
- Git（選配，若不熟悉指令可直接下載 ZIP 檔）
- Microsoft Word（或相容之文書處理軟體，如 LibreOffice Writer）
- LibreOffice（若您需要轉檔為 ODT）

### 2. 核心檢索工具安裝：`tw-legal-rag`（重要必備）

本套件的官方裁判與函釋檢索模組（`twlegalrag-search`）建立於開源專案 **[tw-legal-rag (法律偵探 @aa0101181514)](https://github.com/aa0101181514/tw-legal-rag)** 之上。

在啟用 `legal-research` 或 `twlegalrag-search` 技能前，**必須先依照該專案說明在您的本機系統中完成安裝與設定**：

```bash
# 請參考 tw-legal-rag 官方專案指引進行安裝與環境設定
# 專案網址：https://github.com/aa0101181514/tw-legal-rag
```

安裝完成後，確認在終端機執行 `twlegalrag --help` 正常輸出，AI 代理即可在研究過程中自主調用裁判檢索。

### 3. 本專案技能安裝說明

> [!WARNING]
> **不要**將整個 `Legal-Pleading-Suite/` 母目錄直接放入 AI 工具的技能區（Skills folder）。
> 多數 AI 工具只會偵測技能區中「直接可見」的技能目錄與其中的 `SKILL.md`，若您只是把整個解壓後的母目錄原封不動放進去，AI 工具通常**無法正確辨識**位於深層子目錄內的技能。

本專案採 Monorepo 結構管理，真正應加入 AI 工具技能區的，是前述的 **8 個核心技能子目錄**：

- `legal-research/`
- `twlegalrag-search/`
- `draft-pleading/`
- `draft-pleading-const/`
- `legal-opinion/`
- `pleading-table/`
- `docx-to-odt/`
- `pdf-watermark-remover/`

**正確安裝步驟：**
1. 下載或 Clone 整個 `Legal-Pleading-Suite/`。
2. 將上述 8 個子目錄個別移入或軟連結（Junction/Symlink）至您的 AI 工具技能區。
3. 確認每個技能目錄底下都可直接看到 `SKILL.md`。

### 4. 非技能檔案應放哪裡？

下列內容**不是技能**，不需要放進 AI 工具的技能區：
- `README.md`
- `LICENSE.md`
- `examples/`

將整個 `Legal-Pleading-Suite/` 保留在您自己的專案資料夾或工作區中作為說明文件與範本資源即可。

### 5. 進一步深入瞭解（進階參考文件）

本專案將嚴謹的法律撰稿規則與排版邏輯抽離至各模組獨立文件，若您想深入瞭解內部運作準則，請參考：
- **`draft-pleading/references/`**：包含草稿撰寫規則（`phase5-draft-rules.md`）、撰寫計畫要求（`phase3-writing-plan.md`）與第三審書狀攻防（`pleading-third-instance.md`）。
- **`legal-research/references/`**：包含法律見解深度驗證準則（`verify-rules.md`）。
- **`pleading-table/references/`**：包含爭點整理表的詳細排版與自動編號細則（`phase-c-issue-pleading.md`）。
- **`examples/`**：保留兩份階段性產出示例（[`撰寫計畫.md`](examples/撰寫計畫.md) 與 [`訴訟策略備忘錄.md`](examples/訴訟策略備忘錄.md)）。

## 🚀 實戰工作流 (End-to-End Workflow)

本套件採取「人機協作式自動化」設計，依照法律實務的真實邏輯逐步推進：

### 步驟 1：案件資料準備

建議每個案件使用一個獨立工作資料夾，將相關卷證、既有書狀、筆錄、裁判、訪談資料集中管理。
- 支援直接讀取 `.pdf`、`.docx`、`.odt`、`.md`、`.txt` 格式。
- 若有掃描型或文字型 PDF 卷證，可先請 AI 進行 OCR 轉為 Markdown，以提高讀取精確度。
- 可選建立 `案件基本資料.txt` 記錄當事人稱謂、地址、法院、案由等；若基於隱私考量不提供，AI 會自動生成合規之隱私佔位符（如 `原告 [姓名] 住[地址]`），待排版後手動填入。

> [!TIP]
> 若您的系統環境已安裝全域工具 **Pandoc**，通常能進一步提升 AI 對於各類文件格式的轉換成功率與讀取效能。

### 步驟 2：法律問題研究與爭點攻防 (`legal-research`)

將案卷放入工作區後，以自然語言下達指令：

```text
請讀取工作目錄中的案件資料，分析本案的實體與程序爭點，並擬定訴訟攻防策略。
```

或直接提供事實案情：

```text
原告在113年1月1日借給被告50萬元，約定113年12月31日清償，利息年息10%，原告並於同日匯款至被告指定之銀行帳戶，有借據為憑。被告未曾給付利息，也不返還本金。原告於114年11月1日寄發存證信函催告後，被告仍未清償。請分析本案法律問題並擬定訴訟攻防策略。
```

1. **生長式爭點地圖**：AI 梳理事實後拆解爭點，標記 `[待討論]`、`[討論中]`、`[已定案]`。
2. **多輪攻防與實務檢索**：律師與 AI 逐一聚焦爭點進行辯論，按需調用 `twlegalrag-search` 進行正反雙向裁判檢索。
3. **結論即時固化**：律師拍板確認後，AI 自動將結論、裁判字號與攻防要點寫入 `strategy_memo.md`。

### 步驟 3：啟動書狀起草 (`draft-pleading`)

爭點研究完成後，直接在對話中以自然語言指示：

```text
請依據我們方才討論的過程與結論，為原告撰寫一份民事起訴狀。
```

1. **階段性產出 — 撰寫計畫（需確認）**：AI 自動讀取上下文與備忘錄結論，整理訴之聲明、事實經過標題、CRAC 論點大綱與證據編號（原告甲證/被告乙證）。**AI 於此處強制中斷並等待律師確認**（可參考 [`examples/撰寫計畫.md`](examples/撰寫計畫.md)）。
2. **階段性產出 — 書狀 Markdown 草稿（需確認）**：律師確認計畫後，AI 生成結構嚴謹的書狀草稿，嚴格套用狀首動詞表、年份紀元規範與逐字裁判引號。**AI 再次等待律師確認**。

### 步驟 4：自動內部排版與轉檔

律師確認草稿後，AI 自動連續執行內部排版引擎：

```bash
python draft-pleading/scripts/build_pleading.py "草稿路徑.md"
```

- 自動完成 14pt 標楷體、26pt 行高、左側行號與不懸尾標點排版。
- 若需要附表格，自動交接 `pleading-table` 生成高院標準爭點表。
- 若使用者指定 ODT，自動串接 `docx-to-odt` 轉檔並修復 LibreOffice 大綱架構。

## 📐 書狀排版規格與範本調整指南

本套件的最終排版輸出高度依賴預設的 Word 範本檔。使用者可直接開啟下列範本檔查看或調整：

- [`draft-pleading/assets/pleading-tmpl.docx`](draft-pleading/assets/pleading-tmpl.docx)
- [`legal-opinion/assets/opinion-tmpl.docx`](legal-opinion/assets/opinion-tmpl.docx)

### 核心排版規格

- **字型與樣式**：全文預設使用 **標楷體**（英數字自動相容 Times New Roman）。
- **字型大小**：
  - 狀首書狀名稱：**20pt**
  - 正文內容：**14pt**
  - 頁碼、行編號、表格內文字：**12pt**
- **行距與段落**：內文行距固定為 **26pt**。
- **多層次結構**：系統嚴格支援 **四層級自動編號** 結構（`一、` ➔ `(一)` ➔ `1.` ➔ `(1)`），並配合懸掛縮排，確保法條引用與論點層次分明。
- **標點符號控制**：全域關閉「允許標點符號溢出邊界」，嚴格遵守 **標點符號不懸尾**（不超出右側邊界）之規範。
- **行編號（Line Numbering）**：
  - **DOCX 輸出**：行編號固定顯示於頁面 **左側**。
  - **ODT 轉換後**：若經由 `docx-to-odt` 處理，行編號會自動調整為頁面 **外側（Outside）**。
- **表格規格（高院格式）**：
  - 表格係參考 **臺灣高等法院** 的標準格式進行微調，並採直式表格設計。參考來源如下：
    - **爭點整理表、聲請調查證據表**：<https://tph.judicial.gov.tw/tw/cp-11612-2753624-3eb68-051.html>
    - **證據清單**：<https://tph.judicial.gov.tw/tw/cp-11612-2635254-efc7e-051.html>
  - 支援 **跨頁重複標題列**。

> [!IMPORTANT]
> **範本調整重要注意事項**：
> 1. **必須使用 Microsoft Word 進行調整**：若需修改段落樣式或多層次清單，務必使用 Microsoft Word。**請勿使用 LibreOffice Writer 修改範本檔**，因為範本檔案中的「段落樣式」與「多層次清單編號」是高度結合的，使用 Writer 編輯可能會導致兩者分離，造成排版引擎套用失敗。
> 2. **樣式命名規範**：本系統高度依賴範本中以「**書狀**」、「**爭點表**」及「**通用**」為名稱前綴的段落樣式（例如：`書狀_預設`、`爭點表_內容`、`通用_層級1` 等）。這些樣式定義了行高、縮排與對齊邏輯，請勿更名。
> 3. **自訂偏好**：
>    - **行高、縮排與間距**：請直接修改對應的「段落樣式」。
>    - **行編號格式**：在 Word 中是由「**字元樣式**」中的「**行號**」（Line Number）樣式控制。若需調整行編號的字型或大小，請修改該字元樣式。

```text
請將我們討論好的違憲論點素材，套入 draft-pleading-const 生成憲法法庭聲請書。
```

### 4. 轉成 ODT 檔案
```text
請幫我將這份書狀草稿轉成 ODT 檔。
```

### 5. 一鍵批次修復舊 ODT 檔案
若您有舊的 ODT 書狀無法使用 Tab 鍵進行升降級，可直接使用隨附工具：
- **修復單一舊 ODT 檔案**：
  ```bash
  python docx-to-odt/scripts/fix_existing_odt.py "路徑/舊書狀.odt"
  ```
- **批次遞迴修復整個資料夾**：
  ```bash
  python docx-to-odt/scripts/fix_existing_odt.py "你的案件書狀資料夾路徑"
  ```

### 6. 移除法院電子卷證浮水印
```bash
python pdf-watermark-remover/scripts/remove_watermarks.py -i "原審卷宗.pdf" -o "乾淨卷宗.pdf"
```

### 7. 台灣裁判語義檢索與驗證
```text
請幫我查詢最高法院關於違約金過高酌減之實務見解，並進行正反雙向查證。
```
或直接使用 CLI 與引用檢查腳本：
```bash
# 1. 檢索裁判
twlegalrag search "違約金 過高 酌減" -n 5

# 2. 打包判決封包 JSON
twlegalrag pack "違約金 過高 酌減" -o bundle.json -n 10

# 3. 引用正確性驗證
python twlegalrag-search/scripts/check.py bundle.json answer.txt
```
