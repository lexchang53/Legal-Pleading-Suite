# 訴訟書狀撰寫與排版技能 (`draft-pleading`)

接收使用者在對話中與 AI 討論的結論、`legal-research` 技能產出的訴訟策略備忘錄（`strategy_memo.md`）、或使用者直接提供的書狀素材，依嚴格的訴訟書狀格式規範產出結構嚴謹的 `.md` 法律書狀草稿，並在使用者確認後自動執行自身的排版引擎 `python scripts/build_pleading.py` 產出最終 Word/ODT 檔。

---

## 觸發條件

- **新撰書狀**：「書狀」「訴狀」「起訴狀」「上訴理由狀」「答辯狀」「準備書狀」「爭點整理狀」、聲請調查證據
- **修改補充**：「補充」「修改」「增加」「新增論點」，以及**任何要求修改訴訟書狀草稿的指令**（包含重新開新對話，或距離第一次形成草稿後幾天提出的修改），皆應主動適用。

> [!NOTE]
> **狀首欄位規則**（書狀類型與對應欄位的完整判斷表，詳見 `references/phase5-draft-rules.md` 之「狀首欄位排版與生成規則」一節）：
> - **民事起訴狀**：不寫案號/股別；**必寫**訴訟標的金額或價額（金錢請求→「金額」；非金錢→「價額」；混合→「金額及價額」）
> - **民事上訴狀**（正式提起）：寫案號/股別；**必寫**訴訟標的，置於股別之下
> - **有追加聲明或提起反訴**：寫案號/股別；**必寫**訴訟標的，置於案號之上
> - **準備書狀、答辯狀、上訴理由狀**（無追加）：寫案號/股別；**通常不寫**訴訟標的

## 全域強制規則

> [!IMPORTANT]
> **無干擾與連續執行原則**
> 執行本技能時，必須**全流程連續、自主運作，直到 Markdown 草稿產出並交接完畢**。
>
> **允許中斷的時機**（僅以下節點）：
> - 階段 3：撰寫計畫產出後（等待確認）
> - 階段 4：草稿產出後（使用者確認後自動進入階段 5 排版）
> - 修改補充模式步驟 M2：修改計畫產出後（等待確認）
> - 修改補充模式步驟 M3：修改後草稿產出後（等待確認）
> - 遇到無法靠推知補齊的致命缺失
>
> **連續執行規則**：
> 1. 所有無破壞性的 `run_command` **務必設 `SafeToAutoRun: true`**
> 2. 將多檔讀取與分析合併在代理內部自主迴圈

> [!CAUTION]
> **絕對禁止**：
> - 捏造不存在的判決字號、法規條文或證據內容
> - 在頁碼不確定時不留占位符（應使用 `第 [待補] 頁`）
> - 將產出檔案存到 `brain`、`artifacts` 或其他系統目錄（必須存到使用者工作目錄）
> - **無證據時產生證據清單：** 若整份草稿無任何證據及附件引用，【絕對不得】產生「證據或文件清單：」及其後續證據列表。
> - **年份紀元強制規則：** 年份預設不加紀元，但有兩處例外：（1）「聲明」中的年份必須加「民國」前綴；（2）「狀尾日期」（公鑒行之後、具狀人之前）必須使用「**中華民國**」完整前綴。其餘地方（狀首日期、理由段落等）年份前**絕對不加**任何紀元。
> - **誤用既有書狀日期：** 即使使用者 `@` 提供含日期的既有書狀，只要未明確指示日期，一律需重新計算預設日期。
> 
> **書狀格式通則（證據清單、層級順序、單一論點等完整規範）全部詳見 `references/phase5-draft-rules.md`。**

### 爭點整理表專項強化規則

> 爭點整理表相關強制規則（法律依據格式、證據頁碼、調查對象地址、「提出人」稱謂）全部詳見 `references/phase-c-issue-pleading.md`。

## 工作流程

依工作性質分為**新撰模式**（階段 1～5）與**修改補充模式**（M1～M3）。

### 階段 1：接收訴訟素材與前置檢核

1. **確認素材來源**（素材來源可為以下任一）：
   - **`strategy_memo.md`**：由 `legal-research` 技能產出的訴訟策略備忘錄。AI 應主動掃描工作目錄是否存在此檔案並優先讀取。
   - **對話討論結論**：使用者在對話中與 AI 討論後收斂的法律攻防結論與實務見解。
   - **使用者直接提供**：使用者提供的案卷資料（`.md`、`.pdf`、`.docx`、`.odt`）、論點提綱或舊書狀。
2. **前置完整度檢核**：
   - 若工作目錄無 `strategy_memo.md`、對話中無實質討論且使用者未提供具體論點，AI 應提示：「目前缺乏具體的事實與法律論點素材。建議先就案情進行討論、調用 `legal-research` 技能分析爭點、或直接提供論點要旨後再行產出書狀。」
3. **前置動作 A — 讀取案件基本資料**：
   - 優先搜尋工作目錄下名為「案件基本資料」的檔案（限 `.md`、`.txt`），讀取：當事人稱謂、姓名、地址、電話、電子郵件、法院名稱、**案由**。
   - 若無該檔案，再尋找工作目錄中最近日期的書狀檔案（優先 `.md`，次為 `.odt`、`.docx`）擷取上述資訊。
4. **前置動作 B — 卷宗頁碼檢索**：
   - 掃描工作目錄中的既有書狀（優先同名 `.md` 檔），釐清既有證據的卷宗頁碼。若有明確頁碼則帶入；若無則依規定留空或保留編號。

### 階段 2：確認案件資訊與書狀類型

依據讀取到的案由與書狀類型，確認書狀開頭句「為就……事件，……事：」及對應動詞：

| 書狀類型 | 開頭句格式 |
|---|---|
| 起訴狀 | 為就［案由］事件，**起訴**事： |
| 上訴狀 | 為就［案由］事件，**提起上訴**事： |
| 上訴理由狀（首狀：不含序號、或序號為「（一）」） | 為就［案由］事件，**提出上訴理由**事： |
| 上訴理由（二）狀以後（含「（三）」「（四）」等） | 為就［案由］事件，**補充上訴理由**事： |
| 答辯狀（首狀：不含序號、或序號為「（一）」） | 為就［案由］事件，**提出答辯**事： |
| 答辯（二）狀以後（含「（三）」等） | 為就［案由］事件，**再提答辯**事： |
| 準備書狀（首狀：不含序號、或序號為「（一）」） | 為就［案由］事件，**提出準備書**事： |
| 準備書（二）狀以後（含「（三）」等） | 為就［案由］事件，**再提準備書**事： |
| 爭點整理狀 | 為就［案由］事件，**整理爭點**事： |
| 聲請調查證據狀 | 為就［案由］事件，**聲請調查證據**事： |
| 其他書狀 | 依書狀內容自行判斷合適的動詞組合 |

### 階段 3：產出撰寫計畫（強制中斷並等待確認）

**執行前讀取** `references/phase3-writing-plan.md`

**不可遺漏的強制規則**：
1. **強制輸出為實體檔案**：若判斷需要生成撰寫計畫，**必須**使用 `write_to_file` 工具建立 `implementation_plan.md`（設 `IsArtifact: true`），檔案將在編輯器中開啟供檢閱。產出後必須在對話框明確告知：「撰寫計畫已產出，請檢閱後回覆。」
   > **確認判斷規則**：空白訊息（輸入一個空白鍵後按 Enter）或單一短字（「確認」「好」「ok」「y」「是」）→ **視為確認**，進入下一階段。任何指含實質內容或訊息超過一句的回覆 → **視為修改意見**，進入修改流程。
   > **提醒**：輸入一個空白鍵後按 Enter 即可確認；如需修改，請直接提出意見。
2. 起訴狀**必須**包含：聲明、具描述性標題之「事實經過」段落、請求權基礎。
3. 勞動訴訟原告**不寫假執行宣告**。
4. 論點大綱的層級順序必須與最終書狀一致（`一、` → `(一)` → `1.` → `(1)`）。

> [!CAUTION]
> **絕對中斷點：在使用者明確回覆「確認撰寫計畫」或等同同意之指令前，絕對禁止進入後續階段，更不允許提前生成書狀草稿。**

### 階段 4：生成書狀草稿（需使用者確認）

> [!CAUTION]
> **進入本階段前，必須先讀取格式規範**：必須先讀取 `references/phase5-draft-rules.md`（含強制預檢清單、四類黃金範例、完整格式規範）。不讀取此文件，發生格式錯誤是**必然的結果**。若撰寫**爭點整理狀**，改為讀取 `references/phase-c-issue-pleading.md`。

1. **草稿撰寫規範**：
   - 嚴格依照 CRAC（結論先行、法條與裁判依據、事實涵攝、結論）展開段落。
   - 正式裁判字號引用（如 `最高法院 112 年度台上字第 9 號民事判決`）必須附引號「」節錄原文。
   - 證據與清單接續編號。
2. **草稿格式強制預檢**：
   - 草稿撰寫完畢後，AI 必須依據 `phase5-draft-rules.md` 預檢清單自我審核。呈現在對話框時**「僅限輸出單行結論」**，例如：`[✅ 草稿預檢完畢：引用格式與標題層級皆符合規範]`。
3. **實體檔案寫入與確認**：
   - 產出草稿時，必須設 `IsArtifact: true` 並使用 `write_to_file` 直接寫入工作目錄。產出後明確告知：「書狀草稿已產出至您的工作目錄，檔案將在編輯器中開啟供檢閱。請檢閱後回覆。」
   > **確認判斷規則**：空白訊息或短字（「確認」「好」「ok」）→ **視為確認草稿**，進入階段 5 排版。任何含實質內容的回覆 → **視為修改要求**。

> [!CAUTION]
> **絕對中斷點**：絕對禁止在使用者尚未確認草稿（或尚未確認「修改後」的草稿）的情形下，逕自呼叫腳本產出 DOCX。

### 階段 5：保存草稿並自動內部排版

在獲得使用者對草稿的明確確認後，**連續執行以下步驟，中間不得再向使用者確認**：

1. **檔名生成規則（強制附加 _草稿）**：保存草稿前，分析工作目錄現有書狀命名規則（例如「案號＋書狀名稱」），**必須在主檔名後方強制加上 `_草稿` 作為後綴**（例如 `26-0511-黃清波等三審上訴理由三狀_草稿.md`）。
2. **依書狀類型分流決策**：
   - **一般書狀** 或 **未要求附表格之爭點整理狀** → **直接呼叫內部腳本產出**，執行：`python scripts/build_pleading.py <草稿完整路徑>`，由本技能專屬引擎進行最終 Word 渲染。
   - **爭點整理狀 + 使用者明確要求附表格**（下半部含 JSON）→ **自動呼叫 `pleading-table` 技能**，由其提取下半部 JSON 並生成含爭點表格的最終 DOCX。
3. **自動接續轉檔 ODT**：若使用者下達指令明確要求產出 `.odt` 檔，在上述 DOCX 生成完成後，**自動再呼叫 `docx-to-odt` 技能**將該 DOCX 轉為 ODT，無需等待使用者分兩次下達指令。

> [!IMPORTANT]
> **排版阻斷自癒機制（最高優先處理，不得向使用者求救）**：
> 若 `build_pleading.py` 執行後輸出 `[ABORT]` 或 `[FAIL]`，AI 必須立刻進入自動修復流程：
> 1. 解析腳本輸出之違規項目（違規類型、所在行號、違規文字）。
> 2. 依錯誤類型對應格式規則，使用 `replace_file_content` 工具直接修正 `.md` 草稿。
> 3. 立即重新執行 `python scripts/build_pleading.py <草稿路徑>`（最多重試 2 次）。

## 修改補充模式

使用者已有書狀，需修改或補充論點。

### M1：確認修改範圍與新證據接續編號
- 讀取現有書狀（`.md` 或 `.docx`）。
- 確認需求：新增 / 修改 / 刪除 / 調整順序。
- **新證據接續編號強制規則**：若使用者提出「新證據」，主動搜尋工作區內現有書狀，檢查目前編排之證據編號（例如上證7），接續往下編排（延續編為上證8）。

### M2：產出修改計畫（需使用者確認）
呈現：現有結構 → 計畫修改 → 修改後預覽。

> [!CAUTION]
> **絕對中斷點**：展示修改計畫後，等待使用者回覆後才進行 M3，**絕對禁止**在尚未確認的情形下直接產出草稿或 DOCX 檔。

### M3：更新草稿並內部排版（需使用者確認）
1. 依確認的計畫輸出更新後的完整 Markdown 草稿（設 `IsArtifact: true` 並寫入工作目錄）。
2. **強制更新日期**：嚴格依照【狀首與狀尾日期生成規則】重新生成並覆寫草稿中的狀首與狀尾日期。
3. **確認後才排版**：確保使用者確認「修改後的最新草稿」後，才呼叫內部專屬腳本 `scripts/build_pleading.py` 完成最終排版，**嚴禁未經確認前偷跑轉檔**。
